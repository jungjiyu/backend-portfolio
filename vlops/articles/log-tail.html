작업 종료 후 로그 누락: drain과 타임아웃 설계

GPU 작업이 종료된 뒤 로그를 대조하자, 재접속 검증은 통과했는데도 마지막 오류 로그가 빠져 있었다. 작업 종료를 감지한 클라이언트가 아직 읽지 않은 로그 스트림까지 닫고 있었기 때문이다. 종료 감지 후 남은 출력을 수집하는 drain 상태를 추가하고, 재접속 중에도 유지되는 타임아웃을 적용했다.

재접속 검증을 통과한 로그에서 발견한 누락

NAVER Cloud에서 VLOps의 원격 로그 follow 기능을 구현했다. 연결이 끊기면 로그 서버가 처음부터 다시 전송했으므로, 클라이언트는 이미 전달한 구간을 검증한 뒤 건너뛰어야 했다. 같은 메시지가 정상적으로 반복될 수 있어 문자열만으로 중복을 제거할 수는 없었다.

전달한 레코드 수와 누적 해시를 저장하고, 재접속 후 스트림 종류와 본문을 같은 순서로 해시에 반영했다. 이전에 전달한 개수까지 읽었을 때 해시가 일치하면 이후 레코드부터 출력했으며, 일치하지 않으면 오류로 처리했다.

이 검증은 이미 전달한 구간이 같은 순서로 재전송됐는지 확인했다. 그러나 작업 종료 후 원격 로그와 전체 출력을 대조하자 마지막 오류 로그가 빠져 있었다. 재전송 구간의 일치는 그 이후 로그까지 모두 수집했다는 근거가 될 수 없었다.

작업 종료를 로그 수집 완료로 처리한 문제

원인을 추적해 보니, 클라이언트가 상태 조회에서 작업 종료를 확인하는 즉시 로그 스트림도 닫고 있었다. 원격 작업의 종료 시점과 클라이언트의 로그 수집 완료 시점을 동일하게 처리한 것이 원인이었다. 작업이 끝났더라도 스트림에는 아직 읽지 않은 출력이 남을 수 있었다.

재접속 시 비교한 해시는 이전에 전달한 구간만 포함하므로, 종료 직전의 새 로그가 누락돼도 검증을 통과했다. 따라서 작업 상태와 별도로 로그 수집의 종료 조건을 정의해야 했다.

drain 상태와 두 가지 타임아웃

작업 종료를 감지하면 즉시 연결을 닫는 대신, 로그 클라이언트를 남은 출력을 읽는 drain 상태로 전환했다. 이때 재접속이 발생해도 drain 상태와 최초 종료 감지 시점을 유지해, 연결 복구가 종료 대기를 초기화하지 않도록 했다.

대기에는 두 가지 제한을 적용했다. idle timeout은 새 레코드를 받을 때마다 갱신해 후속 출력을 기다리고, 전체 대기 한도는 최초 작업 종료 감지 시점부터 계산했다. 유지 중인 서빙 자원이 계속 로그를 보내더라도 전체 한도를 넘겨 기다리지는 않도록 한 것이다.

원격 스트림이 먼저 끝나면 즉시 종료했으며, 로그 연결을 닫는 처리는 GPU 작업의 취소·회수와 분리했다. 전체 대기 한도가 지나면 로그가 더 도착하더라도 수집을 종료한다.

종료 후 전체 출력 대조

작업 종료 후 원격 서버에서 다시 받은 로그와 follow 출력을 바이트 단위로 비교했다. 수정 전에는 마지막 오류 로그가 빠졌지만, drain을 적용한 뒤에는 마지막 줄까지 일치했다.
